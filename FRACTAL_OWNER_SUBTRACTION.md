## 1. W3C PROV — provenance interchange

Official source:
`https://www.w3.org/TR/prov-o/`

W3C PROV already defines a general provenance vocabulary around:
- **Entity**;
- **Activity**;
- **Agent**;
- derivation;
- generation;
- attribution;
- delegation;
- qualified influence relationships;
- links/bundles between provenance descriptions.

That overlaps directly with the first RFC's candidate:
- process;
- principal;
- derivation;
- who acted on behalf of whom;
- what output was generated by which activity.

### THR consequence

THR should **not** invent a competing universal process/principal ontology.

Candidate mapping:

```text
THR source/object/assertion representation
<-> may expose PROV-compatible Entity views

THR process instance
<-> PROV Activity where semantics fit

THR principal / bounded actor
<-> PROV Agent where semantics fit
```

But mapping must remain optional and typed.

PROV does not by itself establish:
- truth;
- moral/legal authority;
- claim-level evidentiary independence;
- living-person publication permission;
- THR-specific correction semantics.

```text
PROV INTEROPERABILITY
!=
THR RECORD MEANING REPLACED BY PROV
```

### Owner-subtraction result

```text
GENERIC ENTITY / ACTIVITY / AGENT PROVENANCE VOCABULARY
-> STRONG OWNER FOUND: W3C PROV

THR RESIDUE
-> evidentiary state
-> claim/source independence
-> correction / unknowns
-> authority boundaries
-> materiality-bounded recursion
-> privacy / anti-enumeration
```

## 2. C2PA Content Credentials — signed digital-asset provenance

Official source:
`https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html`

C2PA already owns a substantial part of digital media provenance:
- assertions about creation / transformation;
- claims;
- claim signatures;
- manifests / Content Credentials;
- cryptographic hard bindings;
- soft bindings / fingerprints / watermarks;
- asset ingredients;
- provenance history;
- signer identity trust model;
- repository receipts;
- AI disclosure assertions.

C2PA explicitly separates cryptographically verifiable provenance/tamper evidence from the
consumer's final judgment about whether the assertions are true.

That is strongly aligned with THR's:

```text
SIGNATURE != TRUTH
HASH != TRUTH
PROVENANCE != TRUTH
```

C2PA also now recommends external identity specifications for human/organizational
identity rather than treating its core claim-signer model as a universal person identity
system.

Official identity recommendation:
`https://spec.c2pa.org/specifications/specifications/2.4/identity/identity.html`

### THR consequence

For C2PA-enabled digital assets, THR should prefer to:
- preserve / reference the Content Credential;
- record which manifest/claim was inspected;
- preserve validation result and limitations;
- relate C2PA asset provenance to THR source/assertion state;

rather than inventing its own signed media-provenance container.

Possible future THR relation:

```text
SOURCE / DIGITAL OBJECT
-> EXTERNAL PROVENANCE OBJECT: C2PA MANIFEST
-> THR OBSERVATION OF THAT MANIFEST
-> THR ASSERTIONS / FINDINGS REMAIN SEPARATE
```

THR still has residue C2PA does not aim to solve:
- ancient/historical sources;
- physical objects without native digital provenance;
- source-ancestry reconstruction after the fact;
- competing assertions across institutions;
- living-practice/community authority;
- claim-level independence;
- bounded negative findings;
- record correction / disagreement;
- unknowns and unexamined material.

### Owner-subtraction result

```text
DIGITAL MEDIA CLAIM / SIGNATURE / BINDING / MANIFEST PROVENANCE
-> STRONG OWNER FOUND: C2PA

THR SHOULD INTEROPERATE
NOT REIMPLEMENT
```

This directly supports Mark's concern that watermarking/SynthID alone cannot solve the
wider problem. C2PA is broader than a watermark, but even C2PA deliberately provides
trust signals rather than a universal truth verdict.

## 3. W3C Verifiable Credentials — cryptographically secured claims

Official source:
`https://www.w3.org/TR/vc-data-model-2.0/`

The Verifiable Credentials Data Model 2.0 already defines a generic ecosystem for
cryptographically secured claims involving:
- issuers;
- holders;
- verifiers;
- credential subjects;
- extensible claim data;
- proof / tamper-resistance;
- privacy and security considerations.

### THR consequence

If THR ever needs to ingest or refer to a formal credential, it should not create a
parallel credential grammar.

Examples:
- an institution asserts custody;
- a laboratory issues a signed calibration credential;
- a professional body asserts a qualification;
- an archive issues a preservation receipt.

Those could be external credentials referenced by THR.

THR should still preserve:

```text
VALID CREDENTIAL
!=
CLAIM TRUE IN EVERY CONTEXT

ISSUER AUTHENTICATED
!=
ISSUER HAS LEGITIMATE AUTHORITY FOR ALL CLAIMS
```

### Owner-subtraction result

```text
GENERIC CRYPTOGRAPHIC CREDENTIAL FORMAT
-> STRONG OWNER FOUND: W3C VC

THR RESIDUE
-> whether credential is relevant
-> authority scope
-> conflicting evidence
-> correction
-> ancestry
-> privacy/publication
```

## 4. W3C DIDs — decentralised identifier/control mechanism

Current W3C family:
- DID Core v1.0 Recommendation:
  `https://www.w3.org/TR/did-core/`
- DID Core v1.1 is a 2026 Candidate Recommendation Snapshot.

DIDs already provide:
- decentralised identifier syntax;
- DID documents;
- verification methods;
- services;
- controller/control semantics;
- key rotation / method-specific operations.

### THR consequence

Do not invent a generic decentralised digital identity protocol.

A DID may be one **external identifier/control mechanism** for some THR principals or
objects where a real owner already uses it.

It should not become:
- mandatory;
- the THR entity ID;
- a universal person number;
- proof that the controller is the claimed real-world person;
- permission to publish or aggregate.

```text
DID CONTROL
!=
REAL-WORLD IDENTITY CERTAINTY
!=
THR PUBLICATION AUTHORITY
```

For living people, the current anti-enumeration rule is stronger than convenience.

### Owner-subtraction result

```text
GENERIC DECENTRALISED CONTROL IDENTIFIER
-> STRONG OWNER FOUND: W3C DID

THR SHOULD MAP / REFERENCE WHEN EARNED
NOT REQUIRE
```

## 5. in-toto + SLSA — process / software supply-chain attestations

Official sources:
- `https://in-toto.io/docs/specs/`
- `https://slsa.dev/spec/v1.2/provenance`

SLSA defines provenance as verifiable information about where, when and how software
artifacts were produced.

in-toto provides a general attestation framework used to express software supply-chain
claims.

This overlaps strongly with THR's first self-description microcase:

```text
VALIDATOR SOURCE
-> EXECUTION PROCESS
-> INPUT CHECKOUT
-> OUTPUT RECEIPT
```

### THR consequence

The experimental validator receipt should **not** evolve into a bespoke THR software
supply-chain attestation format unless a real gap survives.

A future implementation path should test whether the self-description receipt can be
represented as:
- in-toto Statement + predicate;
- SLSA provenance where the process is genuinely build-like;
- or a THR-specific evidence envelope that references one of those external objects.

The current THR microcase contains things software supply-chain provenance does not
necessarily answer:
- THR-specific warnings;
- whether validation has epistemic authority;
- record-level correction semantics;
- historical-claim meaning.

Those can remain THR-local.

### Owner-subtraction result

```text
SOFTWARE PROCESS / BUILD PROVENANCE
-> STRONG OWNERS FOUND: in-toto + SLSA

THR SELF-DESCRIPTION
-> INTEROPERATE FIRST
-> ADD ONLY RECORD-SPECIFIC RESIDUE
```

## 6. Sigstore / Rekor — software signing and transparency logs

Official sources:
- `https://docs.sigstore.dev/`
- `https://docs.sigstore.dev/logging/overview/`

Sigstore provides signing identity infrastructure.

Rekor provides an append-only transparency log for software-signing metadata, with
inclusion proofs and third-party auditing/monitoring.

This overlaps with the RFC's candidate:
- key/signature handling;
- transparency anchor;
- append-only witness;
- externally verifiable checkpoint.

Sigstore documentation also makes an important limitation visible: long-term trust in a
transparency log depends on monitoring; a log operator can have more room to fake
timestamps over short windows than once independent monitoring/checkpoint history exists.

### THR consequence

Do not build a custom transparency log simply because "anti-rewrite" sounds important.

For software/release/process artifacts where Sigstore fits, THR should test external
anchoring there first.

For non-software historical records, the relevant stronger owner may instead be:
- an institutional archive;
- signed Git history;
- archive capture;
- another transparency service;
- a national library;
- a preservation network.

```text
TRANSPARENCY LOG ENTRY
!=
TRUTH

INCLUSION PROOF
!=
CLAIM VALIDITY

APPEND-ONLY LOG
!=
INDEPENDENT GOVERNANCE
```

### Owner-subtraction result

```text
SOFTWARE SIGNING + PUBLIC TRANSPARENCY LOG
-> STRONG OWNER FOUND: SIGSTORE / REKOR

THR SHOULD ANCHOR EXTERNALLY WHERE FIT
NOT RUN ITS OWN LOG BY DEFAULT
```

## 7. Memento — web resource version/time negotiation

Official source:
`https://mementoweb.org/guide/quick-intro/`

Memento / RFC 7089 already defines an HTTP model for:
- Original Resource;
- TimeGate;
- datetime negotiation;
- prior archived versions / Mementos;
- links back to originals.

The current THR Source Model already names Memento as a stronger owner.

### THR consequence

THR should not invent a parallel historical-web version protocol.

For source survival:

```text
THR SOURCE ID
-> live locator(s)
-> observation(s)
-> Memento / archive route(s) where available
```

THR's distinct contribution remains recording:
- what state it actually observed;
- which version mattered to a claim;
- what changed;
- what remained unexamined.

### Owner-subtraction result

```text
WEB DATETIME VERSION DISCOVERY
-> STRONG OWNER FOUND: MEMENTO

THR = CONSUMER / ROUTER / EVIDENCE LAYER
```

## 8. Software Heritage / SWHID — intrinsic software identity and preservation

Official sources:
- `https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html`
- `https://www.softwareheritage.org/software-heritage-faq/`

SWHIDs provide persistent, intrinsic identifiers for software objects using cryptographic
hashes and a Merkle-DAG model.

They distinguish identifier from URL and support contextual qualifiers/anchors.

The SWHID family became ISO/IEC 18670 in 2025.

### THR consequence

For preserved software artifacts, do not mint a new THR content identifier as a
replacement for SWHID.

Use:

```text
THR SOURCE / PROCESS REFERENCE
-> SWHID external identifier
-> optional THR observation / assertion / process relation
```

THR's opaque ID can still provide a stable cross-record referent if needed, but SWHID is
the stronger intrinsic software identity owner.

### Owner-subtraction result

```text
INTRINSIC SOFTWARE OBJECT ID + ARCHIVAL PRESERVATION
-> STRONG OWNER FOUND: SOFTWARE HERITAGE / SWHID

THR SHOULD LINK
NOT REPLACE
```

## 9. Revised architecture boundary

After strongest-owner subtraction, the fractal RFC should become **smaller**, not larger.

Candidate external-owner map:

```text
GENERIC PROVENANCE ENTITY / ACTIVITY / AGENT
-> W3C PROV

SIGNED DIGITAL MEDIA PROVENANCE
-> C2PA

GENERIC CRYPTOGRAPHIC CREDENTIALS
-> W3C VC

DECENTRALISED CONTROL IDENTIFIERS
-> W3C DID

SOFTWARE PROCESS / BUILD ATTESTATION
-> in-toto / SLSA

SOFTWARE SIGNING TRANSPARENCY
-> Sigstore / Rekor

WEB VERSION-TIME ROUTING
-> Memento

SOFTWARE INTRINSIC ID + ARCHIVAL OWNER
-> Software Heritage / SWHID
```

THR should therefore focus on the **joins and residue**:

```text
WHAT KIND OF OBJECT / CLAIM ARE WE TALKING ABOUT?

WHICH EXTERNAL PROVENANCE / CREDENTIAL / ARCHIVE OBJECT APPLIES?

WHAT DID THR ACTUALLY OBSERVE?

WHAT DOES THE SOURCE OR CREDENTIAL ACTUALLY ASSERT?

WHICH EVIDENCE IS INDEPENDENT FOR THIS PARTICULAR CLAIM?

WHAT AUTHORITY IS RELEVANT TO THIS PARTICULAR FUNCTION?

WHAT CHANGED?

WHAT IS DISPUTED?

WHAT REMAINS UNKNOWN OR UNEXAMINED?

WHAT DOWNSTREAM RECORDS SHOULD BE REVISITED?

WHAT PRIVACY / CONSENT / CULTURAL-CONTROL BOUNDARY APPLIES?

CAN A FUTURE READER CONTINUE WITHOUT TRUSTING THE CURRENT THR OPERATOR?
```

This is a more defensible THR contribution than inventing another general provenance
standard.

## 10. What the "fractal" idea becomes after subtraction

The fractal is **not** one giant THR-native ontology.

It is a recursive ability to descend into whichever stronger object owns the next layer.

Example:

```text
THR ASSERTION
-> THR SOURCE
-> C2PA MANIFEST
-> C2PA CLAIM SIGNER / BINDING

THR PROCESS RECEIPT
-> in-toto / SLSA provenance
-> Sigstore signing receipt
-> Rekor inclusion proof

THR WEB SOURCE
-> Memento TimeGate
-> archived version

THR SOFTWARE SOURCE
-> SWHID
-> Software Heritage archive
```

Then THR returns to its own job:
- relation to the bounded claim;
- correction state;
- independence;
- unknowns;
- rights/authority;
- consequences.

```text
FRACTAL THR
!=
THR OWNS EVERY LAYER

FRACTAL THR
=
THR CAN FOLLOW AND PRESERVE THE JOINS
WITHOUT FLATTENING THEIR DIFFERENCES
```

## 11. New hostile questions earned by owner subtraction

1. Can THR map to PROV without turning every local node into a global `prov:Entity`?
2. Can THR ingest C2PA without treating a valid manifest as proof the depicted event is real?
3. Can a VC issuer be authentic but lack legitimate authority for the bounded claim?
4. Can a DID controller rotate keys without THR silently changing entity identity?
5. Can SLSA/in-toto describe the process while THR separately preserves validator warnings and epistemic ceilings?
6. Can a Rekor inclusion proof remain operational evidence rather than historical-claim evidence?
7. Can a Memento capture be byte-preserved while its original publication context remains uncertain?
8. Can a SWHID identify exact software bytes while authorship/licence/governance remain separate assertions?
9. Can THR preserve interoperability mappings without making external standards mandatory?
10. Can the public record remain intelligible if those external systems disappear later?

These are stronger next tests than inventing more THR-native object types.
